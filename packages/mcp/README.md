# GitDocket MCP server

Install with Node 22 or later: `npm install -g --include=optional @gitdocket/cli @gitdocket/mcp`. The `docket-mcp` command uses the same standalone release as the CLI and needs no separate Bun installation. Supported platforms are macOS and glibc Linux on arm64/x64.

`docket-mcp --version` reports the installed release. Run `docket init --agent cursor --agent claude --agent codex` from the CLI to prepare supported project integrations, or configure your host to launch `docket-mcp` in the project directory. The server keeps stdout reserved for MCP messages. See [npm installation and migration](https://github.com/GitDocket/gitdocket/blob/main/docs/npm.md).

In GitDocket 0.6.4, `overview` defaults to the bounded `agent-overview/v1` briefing. Pass `{ "view": "full" }` for the previous response model and state-of-play refresh. Brief selections include omitted counts and exact source paths; read the authored context's review status before relying on it. The default JSON projection has a 16 KiB UTF-8 budget, with explicit additional omissions and excerpt reduction; next-work identity and coordination warnings remain intact. Exact `source_page` continuations and the full view retain detail access. Compact writes and lint summaries have separate 8 KiB budgets. CLI-only compact pickup has a 32 KiB budget; MCP does not acquire lifecycle tools from that feature. Advertised tool-schema/instruction bytes are distinct from material actually loaded by a host. The opt-in CLI context review analyzes only supplied exports and does not add a polling loop or MCP tool.


Ordinary wiki authoring uses `document_create` (path/type/title/body and optional description/tags), `document_read` (path and optional section), and `document_edit` (path/expectedVersion/patch). Creation supports Reference, Spec and Playbook only and refuses occupied or owned locations. Reads return complete source bodies and versions; saves reject stale versions and patch body, section, title or description. Call `index` after changes to regenerate discovery, then `lint`. These tools do not select tracked work or activate guidance. Read the installed `workflows/docket-wiki.md` for duplicate resolution and linking judgment.


Record an accepted choice with `decision_create`: required `title`, optional `description`, `tags`, `context` (including alternatives), `decision` (choice and rationale), and `consequences`. It returns `{id, path}` and writes an accepted Decision with a UTC timestamp under `decisions/`; omitted sections contain placeholders to complete. IDs use configured `ids.decision_prefix` (default `DEC`) and an independent sequence when that prefix differs from the project key. Identical prefixes share reservations. The same linked-worktree coordination and exclusive destination protection apply to `task_create`, which accepts only Task or Epic.

After recording, use `document_read` to verify the complete source, then `index` and `lint`. For example, call `decision_create` with `{"title":"Use nightly CSV imports","context":"Considered nightly CSV and real-time events; upstream supplies nightly files.","decision":"Use CSV to avoid delaying launch.","consequences":"Onboarding waits for the nightly run; revisit events when a feed exists."}`. Read the installed `workflows/docket-task.md` for creation judgment. Recording neither starts work nor changes an active-task marker or project guidance. The matching CLI operation is `docket decision create`.


Move an ordinary wiki path with `document_move_plan` (`from`, `to`), inspect its paths/replacements/blockers/warnings, then call `document_move_apply` with `from`, `to`, and `expectedVersion: plan.version`. Title-only edits use `document_edit`. Apply recomputes the complete bundle snapshot, repairs supported Markdown inline/image/reference destinations and relative outbound targets, and refreshes the index. Protected/owned sources, collisions and stale snapshots are refused; code and metadata stay unchanged, and affected unsupported reference forms require explicit reconciliation. Outside references remain unmanaged.

When the result has `state: recovery_required`, retain its receipt and call `document_move_recover` with `token: recoveryToken`. Original and planned bytes remain in the returned `<bundle>/.docket-moves/<token>.json` journal. Recovery validates the plan and accepts only original or planned bytes; unrelated edits require explicit reconciliation. Journals are local recovery material to retain until verified and review before committing or archiving. These operations do not commit, select tracked work or activate guidance. Read the installed `workflows/docket-wiki.md` for the complete workflow.

In GitDocket 0.6.4, review Docket records from a local branch with `reconcile_plan` and `selection: {sourceRef, paths}`. An optional absolute `sourceRoot` selects a linked worktree; `saved: true` reads its saved drafts with `sourceRef` resolving to that worktree's HEAD. `baseRef` optionally pins a shared ancestor. Follow plan pages with `offset` and exact source pages using `reconcile_source` with `selection`, `expectedVersion: plan.version`, `path`, `side` (base/local/incoming/proposed) and `offset`. The plan classifies compatible changes, independent logs, derived index content, semantic review and collisions; its epic counts are previews.

Task/Epic creation in GitDocket 0.6.4 accepts `body` in `task_create`. Supply the complete authored Markdown (at most 64 KiB UTF-8) and use `response: "compact"` to receive ID/path and the exact source version after one exclusive source write. Core validation occurs before shared allocation; omission retains the skeleton. Preserve Context links and verifiable Acceptance Criteria, then refresh discovery and lint once after the final batch. Creation leaves active-task state alone. CLI `docket task create --input <file> --compact --json` accepts the same authored body with camel-case `dependsOn`; the JSON also supports title/type/description/epic/priority/rank/assignee/tags/slug. Existing title/type flags remain supported, without mixing them with JSON input.

Call `reconcile_apply` with the selection, expectedVersion and one choice per path: `{path, disposition}` where disposition is keep-local, merge-compatible, take-incoming or resolve. Semantic/conflicting choices require a reason; resolve supplies complete source. Terminal imports additionally require acceptCompletion and valid local transitions/dependencies. Untracked drafts require keep-local or explicit resolution, with originals retained. Source writes and derived index regeneration are journaled under `<bundle>/.docket-reconcile/<token>.json`; retain the receipt and use `reconcile_recover` with its token after an interruption. Recovery refuses unrelated changes, repeated completed application is a no-op, and local journals contain authored originals and review reasons. These operations never fetch, merge application code, commit Git history, remove branches or establish implementation integration. The CLI mirrors them as `docket reconcile plan|source|apply|recover`.

Task lifecycle pickup, closure and scoped stop remain CLI operations; there is no `task_start`, `task_close` or `task_stop` MCP tool. A `set_status` result does not imply lifecycle cleanup. The 0.6.2 CLI close result returns matching scoped cleanup arguments, retains the hook marker until the closure commit, and checks task/workflow identity plus committed terminal source when `--after-commit` is supplied.

MCP `lint` keeps its full diagnostic-array default and offers `view: "summary"`, `changed_paths`, `baseline_path`, `offset` and `limit`. Summaries are bounded to 8 KiB and keep global errors/introduced findings visible. A baseline is a complete saved report inside the selected checkout; the tool does not write reports. Missing or incompatible evidence stays unknown, and differing optional Git/verification coverage leaves those checks unknown while compatible source findings still compare. CLI `lint --summary --report <owned-json-file>` can retain complete local evidence. MCP results expose global counts; CLI `--strict` policy remains a CLI choice, with no hidden-warning exemption.

`index` refreshes generated Markdown discovery only, preserving authored regions and returning a versioned changed/no-op result. SQLite cache publication and verification/Git cache inputs belong to CLI `docket index`; CLI receipts expose fresh-input/cache reuse, actual phase counts and `--rebuild`. Neither surface treats equal Markdown index bytes as proof of other inputs being current.

Compact writes expose `discovery` ownership hints without an extra status call. A changed item can require discovery assessment at the caller's authorized batch boundary; the tool does not write the bundle log or parent epic implicitly. Explicit worker contracts can assign eligible shared updates to integration, preserving required local discovery/validation and nonterminal dependency semantics. Full legacy views and required wiki move/reconciliation repairs remain available.

To edit one level-one section, pass `section: "Current state"` to `document_read`, then use its whole-source version in `document_edit` with `patch: {section: {heading: "Current state", body: "Replacement content."}}`. A section read is not a complete body draft. Do not combine body and section patches; the section body excludes the heading and cannot contain another level-one heading. A missing section is inserted, duplicate headings are refused, and `body: null` removes the section.
