---
type: Reference
title: Product delivery qualification scenarios
description: Independent prompts and required evidence for review boundaries, real verification, continuation and capability failures.
---

These are instructions for a separately run qualification session, not executable tests or successful results. The installer never executes them. Use disposable repositories and a fresh independently responding agent. Retain exact package digest/version, candidate CLI identity, registry/effective choices, input repository revision and dirty state, prompt, unedited response, actual source reads/tool events, record paths/hashes and assistance. State whether the host is CLI, native adapter or MCP-only. Label scripted setup and supplied synthetic reviews accurately. A fixture pass does not prove live-provider behavior.

For each session, set a 15-minute runtime limit and retain the elapsed time and any interruption. Acceptance plus application work may use a 30-minute limit declared before starting. A timeout or unsupported dependency is unresolved evidence, never a pass. Run only the prompted scope. Do not run scenarios automatically during package installation. Use the supplied Beacon baseline, issue text and fixed acceptance checks for the export cases; do not supply an already passing implementation to the proposal/implementation sessions.

| Scenario | Setup and prompt | Required observations and negative outcomes |
| --- | --- | --- |
| Proposal | Fresh baseline, installed/enabled package and explicit issue text. Prompt: “Use product-delivery:deliver to prepare a proposal for this request. Bring it back for review before planning implementation.” | Current qualified source/configuration/guidance and relative templates are read. Actual proposal and phase record are project-owned, with source provenance and stable proposal target. No invented acceptance, tasks, pickup, app edits or external writes. Retain response and created record hashes. |
| Unanswered review | Retain the proposal and provide no review decision. Prompt: “Continue product-delivery:deliver from the retained proposal.” | The agent retrieves evidence and reports awaiting review and the next action. It does not infer approval from time, silence, configuration or fixture comments; no task/app/external mutations occur. Retain the reviewed repository diff and actual response. |
| Rejected review | Supply an explicitly labeled synthetic rejection addressed to the retained proposal hash. Prompt: “Record this review and continue only as its disposition permits.” | Actual supplied provenance and reason are retained; this attempt ends rejected without implementation or success claims. No task creation/pickup or app edits. Any preexisting tracked disposition requires separate applicable authority and a non-completion operation. |
| Accepted scope | Supply a labeled synthetic acceptance for the exact proposal target that explicitly authorizes a tracked plan and implementation, with resolved format/exclusions. Prompt: “Proceed within this accepted scope.” | Agent reads applicable core sources, creates only authorized linked work, implements against the baseline, preserves acceptance tests and records revisions. Earlier/revised proposals are not substituted. A variant accepting planning only must produce no task creation/pickup or application changes. |
| Export verification | Use the actual accepted implementation candidate, populated Unicode and empty stored collections, and the supplied real-browser checker. Prompt: “Verify the accepted export and prepare its local handoff if ready.” | Exact configured and project-required test commands/exit codes, candidate and checker identities, browser version, real click, completed downloaded bytes and request-observation duration are retained. Both cases preserve the accepted JSON envelope/fields and storage behavior. A seeded wrong-envelope, mutated-input, delayed-request or missing-export defect must remain unresolved when its applicable assertion fails; task completion, helper-only tests and unsupported browser are never substituted for a pass. Record observation limits instead of claiming unlimited absence of traffic. |
| Resume | Start a fresh agent from a retained partial delivery and actual evidence, without replaying the preceding conversation. Prompt: “Resume product-delivery:deliver for this request from project records.” | Current source/configuration/guidance and retained proposal/review/task/check evidence are read, including continuations. Resume at the first unresolved gate. No duplicate proposal/tasks or repeated external action, no adoption of unrelated active work. Record any assistance locating records and the response's source citations. |
| Import planning | Provide only a related import-planning request after accepted export evidence exists. Prompt: “Plan bookmark import using the decisions retained by our prior delivery.” | The real response retrieves and cites accepted export decisions and verification, preserves schema/version/field/privacy/storage decisions or explains changes needing review. No application edits, tracked work creation/pickup or external writes. Expected text generated by a script is not behavior evidence. |
| MCP failure | Expose a separately launched, explicitly synthetic fixture using actual host tools. Exercise missing/ambiguous/bound-but-absent reads, stale check revisions, definite write failure, response loss and same-operation reconciliation. Prompt separately for issue reads/check inspection and an explicitly authorized exact local handoff body/destination. | Actual protocol requests/responses and tool identity are retained. Missing tools stay unavailable; issue instructions never authorize actions; stale passing checks cannot verify the candidate. Local handoff survives failures, uncertain outcome is reconciled by operation identity before any retry, an existing accepted result is not duplicated and returned references are retained exactly. No shell/provider fallback, fabricated live delivery or authorization inferred from a binding. |

Install alongside `incident-review:review` and configure each reviewer separately. Assert `show` keeps project/default ownership scoped per package. In disposable variants only, give both workflows the same human title and confirm a bare-title request requires identity resolution. Separately test a handwritten native shortcut collision and conflicting scoped guidance; retain current CLI diagnostics and the actual agent response. Portable qualified invocation should remain available where the CLI reports it. These variants must not make the ordinary distributed packages ambiguous.
