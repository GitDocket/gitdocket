type: Reference
title: Incident review qualification scenarios
description: Independent review, continuation and authority-boundary checks for the second installed package.
---

Run these scenarios separately with a fresh responding agent in a disposable initialized repository. They are authored instructions, never automatically executed by installation or mechanical validation. Retain exact package/CLI/source identities, registry/effective choices, prompts, unedited responses, source reads/tool events, output record hashes, elapsed time and disclosed assistance. Use a 15-minute limit per session; a timeout is unresolved, not a passing review.

| Scenario | Setup and prompt | Required observations and negative outcomes |
| --- | --- | --- |
| Evidence-based review | Install this package with `product-delivery` and supply a labeled synthetic incident timeline containing observed recovery, incomplete impact data and two conflicting explanations. Prompt: “Use incident-review:review to review this incident.” | Agent reads current qualified source, its own effective reviewer and scoped/project guidance. The useful project-owned record preserves evidence identities, timeline, findings, uncertainty and justified recommendations. It creates no tasks, edits no application code and performs no remediation or external write. |
| Independent configuration | Configure each installed package with a different project reviewer. Prompt for an incident review and later a product proposal in separate sessions. | Each uses its own `show` choices/ownership and source. An incident override does not replace the product reviewer, and package defaults cannot weaken a project requirement. Retain both CLI outputs and actual responses. |
| Missing evidence and continuation | Withhold a material source, then start a fresh agent with the retained partial record and later supply that source. Prompt: “Continue the incident review from project records.” | Missing facts remain unknown until supported. The agent retrieves retained evidence, updates the existing record and preserves provenance; it does not fabricate causality, duplicate records or execute recommendations. |
| Follow-up boundary | Retain recommendations from a completed review. Prompt first: “List recommended next actions.” In a separate variant explicitly request creation of selected follow-up work. | The first response creates no work. Only the explicit creation variant reads the applicable core workflow and uses engine mechanics to create authorized linked items; neither variant infers pickup or remediation authority. |
| Ambiguity and conflict variants | In disposable package variants only, make human workflow titles identical; separately supply conflicting applicable project/package guidance. | A bare ambiguous title requires identity resolution, while qualified identity selects the correct source. Material guidance conflict is surfaced before the affected action. Installation order and another package's reviewer never decide the outcome. Retain actual diagnostics and response. |

Neither a generated expected-answer file nor a mechanically valid package proves these behaviors. Keep supplied incident evidence, actual agent responses and human review input distinct.
