type: Reference
title: Incident review record template
description: Structure for a useful project-owned review grounded in actual incident evidence.
---

Write a separate complete project concept outside installed package directories with `type: Reference`, a specific `title` and truthful `description`. Replace these prompts with actual observations and reasoning; this template asserts no incident, review or successful outcome. Link only sources that exist.

# Incident scope and impact

Identify the incident, relevant time window/time zone, affected behavior, established user impact and exclusions. State what remains unknown and distinguish supplied synthetic inputs from live observations.

# Evidence and timeline

For each source record identity, revision or retrieval evidence, provenance, observation time and any limitation. Present the key sequence of events with source links and confidence. Distinguish reported times from directly observed times and preserve material disagreements.

# Findings and contributing factors

Explain what the evidence supports about detection, mitigation, contributing conditions and safeguards. Separate confirmed findings from hypotheses and identify evidence that would resolve them. Preserve useful lessons without claiming unsupported causality or personal blame.

# Recommendations and open questions

Describe specific possible improvements, their rationale, unresolved tradeoffs and supporting evidence. Mark them as recommendations awaiting decision. Record no invented task identifiers, owners' commitments, approved remediation or completed follow-up actions.

# Review target and retained identity

Identify the current required reviewer, stable record revision/hash, review state based on actual input and next action. Preserve review provenance when supplied. List assistance and missing sources. Explicitly state whether any separately authorized follow-up work exists and link it only after actual creation.
